# 개인 노트북 환경에서의 로컬 LLM 금융 자료 해석 성능 평가 최종 보고서

실험 기간: 2026년 9월 14일~16일

보고서 작성일: 2026년 9월 17일

평가 대상: Qwen/Qwen3.5-9B, google/gemma-4-12B-it

외부 API 비교 대상: OpenAI GPT-5.6 Luna

---

## 1. 평가 목적과 범위

### 1.1 평가 목적

본 프로젝트는 개인 노트북에서 실행하는 로컬 대규모 언어 모델이 비트코인 시장 자료와 가상 계좌 기록을 정확하게 해석하고, 그 근거를 지정된 JSON 형식으로 설명할 수 있는지 확인하는 개념 검증, 즉 PoC이다.

출발점은 외부 LLM API가 담당하던 시장 및 계좌 자료 해석을 로컬 환경으로 옮기는 것이었다.
로컬 LLM 실행은 API 사용 비용이 들지 않으며 외부 서비스에 자료를 전송하지 않고 모델을 호출할 수 있다는 장점이 있으나, 설치와 응답 생성이 가능하다는 사실만으로 해당 업무에 적합하다고 판단할 수는 없다.

실제 적용에 앞서 잔액과 주문 상태를 구분하는지, 서로 다른 시간 단위의 가격을 혼동하지 않는지, 손익을 설명할 때 체결 수량과 수수료를 올바르게 반영하는지 확인할 필요가 있었다.

이에 평가의 초점을 수익률에서 주어진 사실을 읽고 설명하는 능력으로 정했다. 동일한 가상 자료를 두 로컬 모델에 제공하고, 비추론과 추론 및 설정 차이에 따라 최종 답변의 완성 여부, 판단 근거 설명의 충족률, 회고, 응답 시간과 자원 사용량이 어떻게 달라지는지 비교했다. 외부 API 모델에도 일부 공통 문항을 제공해 로컬 LLM과의 결과 비교하고자 했다.

본 PoC를 통해 답하고자 하는 질문은 다음과 같다.

1. 약 12GB의 GPU 메모리를 가진 노트북에서 두 모델이 지정된 형식의 최종 답변을 완성할 수 있는가?
2. 답변 형식과 거래 제한을 준수한 경우에도 수치, 출처, 관측 시각과 과거 거래에 관한 설명 오류가 남는가?
3. 추론 모드와 모델별 Best Practice 설정을 적용했을 때 설명 충족률의 개선이 관찰되며, 시간과 메모리 측면에서 어떤 부담이 발생하는가?
4. 현재 자료와 실험 규모를 기준으로 어떤 모델 및 실행 조건을 우선 검토할 수 있으며, 실제 도입 판단에는 어떤 근거가 더 필요한가?

### 1.2 평가 범위

평가 자료는 정답을 원본 수치와 계산식으로 확인할 수 있도록 구성한 가상 사례이다. 실시간 Upbit 계좌를 조회하거나 실제 주문을 전송하지 않았다. 출력의 `buy`, `sell`, `hold`는 자료 해석에 따른 의견이며, 실제 체결 결과를 뜻하지 않는다.

평가에는 JSON 형식 준수, 가용 잔액과 최소 주문금액 등 계산 가능한 제약, 필수 판단 근거 설명, 과거 기록 검토, 시간 및 토큰과 GPU 사용량을 포함했다. 미래 가격 예측, 실제 매매 수익성, 장기 수익률과 위험도, 두 모델의 토론, 실시간 운영 안정성 및 한국어 문체 품질은 포함하지 않았다.

따라서 이번 결과를 비트코인 매매 능력의 순위나 일반적인 금융 지능의 평가로 확대하지 않는다. 또한 점수는 문항별로 지정한 사실을 얼마나 완전하게 설명했는지를 나타낸다. 모든 출력 문장의 정확도나 입력 자료 전체의 정보 손실률을 직접 측정한 값은 아니다.

### 1.3 분석 대상과 근거 자료

본 보고서는 [실험_집계.xlsx]에 정리한 6개 조건의 80 응답과 Luna 비추론 5응답, 총 85응답을 중심으로 분석한다.
로컬 비교의 핵심은 기본 비추론, Best Practice 비추론과 Best Practice 추론 사이에서 설명 충족률과 실행 부담이 어떻게 달라졌는가이다.
한국어 비교와 실행 준비 점검 등은 최종 비교에 포함하지 않는다.

집계표는 조건별 통계, 결과 CSV는 개별 응답과 측정값 및 판정 근거를 제공한다.

문항별 입력과 채점 기준은 cases.json, 공통 지시문은 prompt.py에 정의되어 있다. 이 보고서의 점수는 판정을 집계한 값이며, 점수의 변화와 감점 사유를 함께 설명한다.

## 2. 결과

기본 설정 비추론에서는 두 모델 모두 20회 전부 지시한 JSON 출력을 반환했고, 반환한 의견과 비율은 거래 조건을 충족했다.
그러나 판단 근거 설명 평가는 Qwen 36/60점, Gemma 50/60점으로 사전에 정한 90% 기준에 도달하지 못했다. 답변을 정상적으로 받는 것과 그 설명이 정확한 것은 별도의 문제로 확인됐다.

모델별 Best Practice 설정을 반영한 추론에서는 두 모델 모두 10문항의 최종 JSON을 반환했으며, Qwen은 27/30점, Gemma는 28/30점을 기록했다. 권장 비추론의 17/30점과 22/30점보다 높은 결과였다.

| 비교 조건 | Qwen 판단 근거 설명 평가 | Gemma 판단 근거 설명 평가 | Qwen 응답 시간 중앙값 | Gemma 응답 시간 중앙값 |
| --- | --- | --- | --- | --- |
| 기본 설정 비추론 | 36/60점, 60.0% | 50/60점, 83.3% | 12.700초 | 14.739초 |
| Best Practice 설정 비추론 | 17/30점, 56.7% | 22/30점, 73.3% | 19.023초 | 21.206초 |
| Best Practice 설정 추론 | 27/30점, 90.0% | 28/30점, 93.3% | 186.757초 | 257.727초 |

Best Practice 설정 추론은 가장 높은 설명 충족률을 보였으나 응답 시간도 크게 증가했다. Qwen은 10회 모두 300초 이내에 지정 JSON을 반환했고, Gemma는 6회만 이 기준을 충족했다. 두 모델 모두 최종 답변에 설명 누락이나 지정 항목 밖의 부정확한 표현이 남았다.

현재 노트북에서 300초 내 응답을 요구하는 후속 검토에는 Qwen의 Best Practice 설정 추론을 우선 후보로 제시한다.
판단 근거 설명 평가를 우선하면 Gemma도 비교 가치가 있다.

그다음 Artificial Analysis의 공개 종합 점수와 지시 준수, 긴 자료 활용 등의 세부 평가를 참고했다.

## 4. 시험 자료와 응답 요구사항

### 4.1 가상 자료를 사용한 이유

전체 과거 시세를 길게 전달하면 응답이 틀렸을 때 입력 길이, 자료 구조, 지시문과 모델 능력 중 무엇이 영향을 주었는지 구분하기 어렵다.

이번 평가에서는 오류 여부를 직접 검산할 수 있는 짧은 가상 사례를 구성했다. 잔액 확인, 가격 출처와 시각의 구분, 자료 누락과 과거 거래 검토처럼 서로 다른 상황을 나누고, 각 문항에서 반드시 설명할 사실 세 가지를 지정했다.

본 시험의 로컬 영문 입력은 서버 집계 기준 약 980~1,669토큰이었다. 모델별 토큰화와 추론 모드의 요청 처리 차이로 같은 자료라도 입력 토큰 수는 완전히 같지 않았다.

### 4.2 입력의 구성

| 입력 영역 | 실제 포함한 정보 | 확인하려는 능력 |
| --- | --- | --- |
| `as_of`, `data_notice` | 판단 기준 시각, 가상 자료라는 설명, 제공하지 않은 정보의 추정 금지 | 관측 시점과 자료의 한계 인식 |
| `market_input` | 5분봉, 시간봉과 일봉의 종가, EMA, 거래량, 매수호가와 매도호가 및 각각의 시각 | 시간 단위, 가격 종류와 수치 비교 |
| `strategy_state`  | 가용 및 묶인 잔액, 이전 결정, 주문, 실제 체결, 평가손익과 과거 기록 | 사용할 수 있는 자금과 과거 거래 사실의 구분 |
| `trading_rules` | 가상 수수료율 0.0005, 최소 주문금액 5,000원, 묶인 자금 사용 금지와 자료 누락 시 보류 | 계산 가능한 거래 제한의 적용 |
| `required_observations` | 해당 문항에서 반드시 설명해야 할 세 가지 사실 | 설명 범위의 명확한 지정 |

예를 들어 Q01(문항1)은 가용 현금 1,000,000원, 가용 BTC 0, 묶인 잔액 0인 계좌를 제공한다. 5분봉의 종가는 100,000,000원, EMA는 99,000,000원이며 마감 시각은 2026-09-15 01:00 UTC이다. 이전 결정, 주문과 체결 기록은 모두 빈 배열이다. 모델은 현금과 BTC를 읽는 것에 더해, 가용 잔액과 묶인 잔액을 구분하고 종가가 EMA보다 높다는 사실 및 해당 봉의 마감 시각, 과거 기록 각각의 부재를 설명해야 한다.

공포탐욕지수는 값 68, 분류 `Greed`인 고정 보조 정보로 포함했다. 이 지표의 실제 갱신 시각, 예측력 또는 지표를 추가했을 때의 성능 개선은 평가하지 않았다. 손익 문항에는 체결 기록과 함께 계산된 평가손익도 포함되므로, 평가의 일부는 독립적인 신규 계산 능력보다 주어진 수치 간 관계를 확인하고 설명하는 능력에 해당한다.

### 4.3 문항 구성

| 문항 | 상황 | 확인할 세 가지 사실 |
| --- | --- | --- |
| Q01 | 현금만 보유 | ① 가용 현금과 BTC 및 묶인 잔액 구분 ② 5분봉 종가와 EMA 비교 및 마감 시각 ③ 이전 결정, 주문과 체결의 부재 |
| Q02 | BTC만 보유 | ① 가용 현금 0원과 BTC 0.01 확인 ② 매수 불가와 전량 매도금액 1,000,000원 검산 ③ 종가가 EMA보다 낮다는 사실과 매도 의무의 구분 |
| Q03 | 서로 다른 봉과 거래량 | ① 시간봉과 일봉의 종가 및 EMA 비교 ② 거래량 200→300 BTC의 증가량 100 BTC와 증가율 50% ③ 각 봉의 마감 시각과 호가의 가격 및 관측 시각 구분 |
| Q04 | 최소 주문 경계 | ① 가용 현금 4,999원과 묶인 현금 995,001원 구분 ② 수수료를 포함한 최소 주문 충족 여부 검산 ③ 예약 자금 재사용 금지와 보류 결정 |
| Q05 | 시각과 가격 출처 | ① UTC와 KST 변환 ② 봉 종가와 이후 매수호가 및 매도호가 구분 ③ 기준 시각 이후 관측 자료의 부재 |
| Q06 | 필수 자료 누락 | ① 5분봉과 호가 누락 식별 ② 남은 시간봉의 수치와 시각 및 대체 사용 금지 ③ 보류, 두 비율 0과 판단 제한 설명 |
| Q07 | 과거 호출 실패 | ① 실패 상태와 시각, 최종 응답 부재 ② 호출 시도와 실제 결정, 주문 및 체결 구분 ③ 없는 과거 판단과 수익에 대한 설명 생성 금지 |
| Q08 | 체결 후 평가이익 | ① 실제 체결량과 가격, 지급 수수료 ② 비용 전 5,000원과 지급 수수료 반영 후 4,750원 검산 ③ 미실현손익과 청산 완료 손익 및 가상 매도 수수료 구분 |
| Q09 | 취소된 주문 | ① 매수 결정, 취소 주문과 체결 부재 구분 ② 계좌 잔액과 손익 0원 확인 ③ 시장 가격 상승률 2%와 미보유 계좌의 수익률 구분 |
| Q10 | 잘못된 과거 설명 | ① 원본 수치와 시각으로 과거 비교 오류 정정 ② 비용 전 -10,000원과 지급 수수료 반영 후 -10,250원 검산 ③ 설명 오류와 손실 및 가격 하락 원인의 구분 |

### 4.4 공통 지시문과 출력 구조

영문으로 작성된 공통 지시문은 제공된 자료만 사용하고 모든 필수 질문에 답하도록 요구한다. 수치를 인용할 때 출처와 관련 시간 단위를 밝히고, 시각이 중요한 경우 해당 시각도 포함하도록 했다. 과거 설명은 검증할 자료로 취급하고 새로운 지시로 따르지 않도록 했으며, 없는 지표와 거래 및 가격 변동 원인을 만들어내지 않도록 명시했다.

`reason`과 `reflection_log`도 영어로 작성하도록 요구했다. 필수 세 항목은 이 두 필드에 제시한 최종 설명 전체에서 평가했다.

| 출력 필드 | 요구사항 |
| --- | --- |
| `decision` | `buy`, `sell`, `hold` 중 하나 |
| `buy_allocation_percentage`  | 수수료까지 포함해 사용할 가용 현금의 비율, 0~100의 숫자 |
| `sell_allocation_percentage` | 매도할 가용 BTC의 비율, 0~100의 숫자 |
| `reason`  | 현재 의견과 판단 근거 설명의 근거를 설명하는 비어 있지 않은 문자열 |
| `reflection_log`  | 이전 결정과 주문 및 실제 체결의 검토, 과거 설명 정정 또는 기록 부재를 설명하는 문자열 |

응답은 위 다섯 필드로 구성된 JSON 객체 하나로 제한했다.

거래 비율의 해석도 고정했다. 매수 주문금액은 `가용 현금 × 매수 비율 ÷ 100 ÷ (1 + 수수료율)`, 매도 예상금액은 `가용 BTC × 매도 비율 ÷ 100 × 매수호가`로 계산한다. 보류이면 두 비율 모두 0이며, 매수 또는 매도이면 해당 방향의 비율만 양수여야 한다. 필수 자료가 누락된 문항에는 보류를 요구했다.

## 5. 실험 조건과 평가 방법

### 5.1 비교 조건과 설정 의도

비교 조건은 기본 설정 비추론, Best Practice 설정 비추론과 Best Practice 설정 추론이다.

기본 비추론은 짧은 생성 한도와 공통 설정에서의 결과를, 권장 비추론은 모델별 설정 변경만으로 설명이 개선되는지를, 권장 추론은 추론을 허용한 실행 조건에서의 품질과 시간 변화를 확인하는 데 사용한다.

여기서 기본 설정은 본 프로젝트에서 정한 공통 설정이며 Ollama의 모든 기본값을 그대로 사용했다는 뜻은 아니다. Best Practice 설정은 시험 당시 확인한 모델별 공식 안내를 반영하되, 정상 실행을 위해 정한 문맥 및 생성 한도와 호출 제한을 포함한다.

| 조건 | 모델 | 문맥 창, 토큰 | 생성 한도, 토큰 | temperature / top_p / top_k | presence_penalty | 호출 제한 |
| --- | --- | --- | --- | --- | --- | --- |
| 기본 비추론 | 두 모델 | 8,192 | 2,048 | 0 / 0.95 / 40 | 0 | 300초 |
| Best Practice 비추론 | Qwen | 131,072 | 32,768 | 0.7 / 0.8 / 20 | 1.5 | 1,800초 |
| Best Practice 추론 | Qwen | 131,072 | 32,768 | 1.0 / 0.95 / 20 | 1.5 | 1,800초 |
| Best Practice 비추론 및 추론 | Gemma | 32,768 | 16,384 | 1.0 / 0.95 / 64 | 0 | 1,800초 |

로컬 공통 설정은 seed 42, min_p 0, frequency_penalty 0, repeat_penalty 1이다. Qwen의 생성 한도 32,768과 문맥 창 131,072는 당시 Best Practices 및 Serving 안내를 참고한 설정이다. Gemma의 샘플링은 공식 안내를 반영했으나 문맥 창 32,768, 생성 한도 16,384는 직접 정한 값이다.

문맥 창은 요청을 처리할 수 있는 토큰 공간이고, 생성 한도는 응답 생성에 허용하는 최대량이다. 추론 모드에서는 서버가 반환한 추론과 최종 답변에 생성 예산이 사용되므로, 최종 JSON 자체가 짧더라도 답변 완성까지 더 많은 생성량이 필요할 수 있다.

300초는 운영 요구를 판단하는 기준이고, Best Practice 설정의 1,800초는 답변이 끝나는지 관찰하기 위한 실행 제한이다. 300초를 넘겨 답변한 경우 1,800초 안에 정상 종료했더라도 300초 기준은 미충족으로 집계했다.

### 5.2 반복과 비교 단위

기본 비추론은 영문 10문항을 모델별 두 번씩 호출해 총 40응답을 확보했다. Best Practice 설정은 모델과 모드별로 같은 영문 10문항을 한 번씩 호출해 비추론 20응답과 추론 20응답을 확보했다. Luna는 사전에 선택한 공통 다섯 문항을 한 번씩 호출했다.

| 비교 구분 | 문항 및 반복 | 모델당 응답 수 | 합계 |
| --- | --- | --- | --- |
| 기본 비추론 | 영문 10문항, 각 2회 | 20 | 40 |
| 권장 비추론 | 영문 10문항, 각 1회 | 10 | 20 |
| 권장 추론 | 영문 10문항, 각 1회 | 10 | 20 |
| Luna 비추론 | 공통 영문 5문항, 각 1회 | 5 | 5 |
| 분석 대상 합계 | 조건별 분리 비교 | — | 85 |

각 호출은 이전 대화를 이어받지 않는 독립 요청이다. 회고 문항도 실제 이전 실험의 답변이 아니라 문항에 고정한 과거 기록을 제공한다. 모델과 실행 조건마다 응답 수와 점수 분모를 명시하며, 서로 다른 반복 수를 가진 결과를 하나의 총점으로 합산하지 않는다.

기본 설정 추론은 문맥 8,192와 생성 한도 2,048 또는 4,096에서 최종 답변을 확보하지 못했다. 이 관찰을 바탕으로 더 큰 생성 여유와 모델별 Best Practice 설정에서 답변 완성과 설명 품질을 확인했으며 CSV 파일로 해당 기록을 보관했다.

### 5.3 형식, 거래 제한과 판단 근거 설명의 분리 평가

형식 검사는 다섯 필드의 존재와 자료형, 허용값, 추가 필드와 중복 키를 확인한다.
거래 제한 검사는 반환한 결정과 비율을 가용 잔액, 수수료, 최소 주문금액과 자료 누락 규칙에 대조한다. 이 두 검사는 코드로 수행한다.

판단 근거 설명 평가는 문장을 읽고 원본 수치와 계산 관계를 대조하는 절차이다. CSV에 문항별 기대 설명, 근거 입력 경로, 실제 응답 인용, 판정과 점수를 작성했다.

각 문항은 세 항목으로 구성하고, 항목마다 완전 충족이면 1점, 일부 누락 또는 오류이면 0점으로 처리했다. 수치가 맞더라도 필수 시각이나 출처 또는 계산 관계가 빠지면 `partial`, 잘못된 주장이나 핵심 설명의 부재는 `fail`로 구분했다.

모델당 기본 비추론 총점은 `10문항 × 2회 × 3점 = 60점`, Best Practice 설정의 조건별 총점은 `10문항 × 1회 × 3점 = 30점`이다. 

### 5.4 통과 조건과 비교 우선순위

기본 비추론의 필수 통과 조건은 모델당 20회 중 19회 이상이 300초 안에 지정 JSON을 반환하고, 판단 근거 설명 평가 54/60점 이상을 얻으며 거래 제한 위반이 없는 것이다.

비교는 필수 조건 충족 여부를 먼저 확인한 뒤, 판단 근거 설명 평가, 회고 기록 검토 점수, 응답 시간과 GPU 사용량 순서로 해석한다.

### 5.5 시간, 토큰과 메모리 측정

전체 응답 시간은 모델 로딩, 입력 처리와 추론 및 최종 답변 수신을 포함한다. 로딩 시간, 입력 처리 시간과 생성 시간 및 토큰 수는 별도로 값을 기록한다. 생성 속도는 Ollama 서버가 보고한 생성량과 생성 시간을 기준으로 산출한다.

GPU 전체 사용량은 `nvidia-smi`를 약 1초 간격으로 조회해 관측한 최댓값이다. 응답 후 모델 GPU 적재량은 Ollama에서 별도로 조회한 값이다.

로컬 추론의 생성량은 추론과 최종 답변을 합한 값이며, 두 구간의 토큰 수를 각각 분리한 측정은 아니다. 요청한 생성 한도와 서버가 보고한 실제 생성량은 서로 다른 열에 보존하고, 실제 생성량을 분석에 사용한다.

## 6. 실험 결과

### 6.1 기본 설정 비추론

두 모델 모두 20/20회 지정 JSON을 반환했고, 300초 조건과 반환 결정의 거래 제한 검사도 20/20회 충족했다. 응답 시간 중앙값은 Qwen 12.700초, Gemma 14.739초로 선호 시간 이내였다.

그러나 Qwen의 판단 근거 설명 평가는 36/60점, Gemma는 50/60점이었다. 두 후보 모두 60점 기준에 미달했으며 도입에 적합하지 않음을 보여준다.

Qwen의 경우 BTC를 보유한 계좌를 두고 보유 포지션이 없다고 설명하거나, 매도할 수 있는 BTC를 보유하고 있는데도 매도를 뒷받침하는 근거가 부족하다는 이유로 매도 자체가 불가능하다고 설명한 사례가 있었다.

Gemma의 경우 가용 현금이 BTC 한 개의 가격보다 적다는 이유로 매수가 불가능하다고 설명한 사례가 있었다.

이러한 사례가 있었어도 실제 반환 의견이 `hold`라면 거래 제한 검사에는 통과할 수 있다. 따라서 거래 제한 통과 수는 반환 결정과 비율에 대한 검사 결과이며, `reason`과 `reflection_log`에 적힌 모든 주장이 올바르다는 의미가 아니다.

### 6.2 Best Practice 설정 비추론

Best Practice 설정 비추론은 모델별 10/10회 지정 JSON을 반환했으며 거래 제한도 모두 충족했다.

판단 근거 설명 평가는 Qwen 17/30점, Gemma 22/30점으로 각각 56.7%, 73.3%였다. 기본 비추론 대비 높은 설명 충족률이 관찰되지 않았다.

실제 생성량은 Qwen 187~534토큰, Gemma 154~416토큰이었다. 요청한 생성 한도 32,768토큰과 16,384토큰보다 훨씬 적은 양으로 정상 종료했다. 다만 생성 한도 상향 설정이 비추론 답변의 정확성을 향상시키지는 않음을 확인했다.

응답 시간 중앙값은 각각 19.023초와 21.206초로 기본 비추론보다 길었다.

모든 문항이 개선된 것은 아니다. Qwen Q10은 2/3점에서 1/3점으로 낮아졌고, Gemma Q08은 3/3점에서 2/3점으로 낮아졌다.

응답 시간에서 중앙값은 Best Practice 비추론 대비 Qwen 약 9.8배, Gemma 약 12.2배 상승하였다. Gemma의 Q01, Q02, Q08과 Q10은 300초를 넘겼으며 최대 시간은 Q01의 446.379초였다.

충분한 생성 여유를 둔 Best Practice 설정 추론에서 답변 완성과 설명 충족률의 개선이 관찰되었다.
그러나 기본 설정과 비교할 때 문맥 창, 생성 한도, 샘플링과 시간 제한을 함께 변경했기에 추론 기능 하나가 개선을 일으켰다고  단정할 수 없다.

평가이익 계산 | 체결 가격과 평가 가격을 사용해 수수료 반영 전후 이익 검산 | 이익이 5,000원이고 수수료 반영 후 4,750원이라고 적었지만, 가격 상승분 1,000,000원 × 보유량 0.005 BTC = 5,000원, 여기서 지급 수수료 250원을 빼면 4,750원이라는 계산 과정을 최종 답변에 설명하지 않았다. |

지정 항목 밖의 오류도 남았다. Qwen Q06은 시간봉을 소개하는 문장에 일봉 경로를 함께 사용했다. Gemma Q09는 주문 생성 시각을 취소 시각처럼 표현했고, Q05에서는 매수 의견을 실제 주문 실행으로 읽힐 수 있게 서술했다. Gemma Q08에는 제한된 관측 자료만으로 가격이 안정적이라고 표현한 문장도 있었다.

### 6.6 외부 API 비교와 호출 비용

Luna에는 Q01, Q03, Q06, Q08과 Q10을 각각 한 번 제공했다. 추론은 `none`, temperature는 0, 생성 한도는 2,048토큰과 호출 제한 300초였다. 다섯 응답 모두 지정 JSON과 거래 제한을 충족했고 판단 근거 설명은 15/15점, 회고는 6/6점을 얻었다. 전체 응답 시간은 평균 8.539초, 중앙값 8.007초였다.

다만 다섯 문항 한 번씩의 관측이며 로컬과 외부 API의 내부 설정과 계산 자원은 같지 않다. 이 결과가 외부 API 모델의 일반적인 무오류 성능이나 실제 매매 우위를 입증하지는 않는다.

다섯 호출의 사용량은 입력 5,900토큰, 출력 1,939토큰이며 추론 토큰은 0이었다. 당시 기록된 단가와 사용량을 적용한 비용 합계는 **USD 0.00375315**, 한 호출 평균은 **USD 0.00075063**이다. 같은 입력 및 출력 규모에서 모델 하나를 하루 24시간, 30일 동안 30분마다 호출하면 약 $1.08, 1시간마다 호출하면 약 $0.54로 환산된다.

이는 이번 비추론 사용량과 기록 단가에 따른 계산이며 현재 가격을 새로 조회한 견적이나 청구서 확정 금액은 아니다. 입력과 출력 길이, 캐시 및 재시도에 따라 비용은 달라진다.

실험의 한계

첫째, 가상 문항은 잔액과 시간, 출처 및 손익의 대표 상황을 투영하지만 실제 시장의 데이터 누락, API 장애, 급격한 시세 변동과 장기간의 복잡한 거래 이력을 포괄하지 않는다.
